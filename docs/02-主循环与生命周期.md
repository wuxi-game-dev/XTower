# 02｜主循环、生命周期与时间

## 1. 谁在“泵”游戏

先读[00｜从双击到第一帧](00-从双击到第一帧.md)。你以前可能在 Unity 中把 `Update()` 想成引擎每帧调用的方法。在 Godot 也是引擎驱动，而不是脚本自己写 `while (true)`：平台的运行循环持续调用 Godot 的一次迭代；默认 `SceneTree` 作为 `MainLoop` 管理运行中的节点。

一个**概念化**的循环如下；它帮助理解职责，省略了多线程、输入缓冲和各服务的内部同步：

```text
while (窗口/进程仍在运行) {
    平台收集窗口和设备事件；
    计算距上次迭代经过了多少真实时间；
    把输入事件送入 Godot；
    根据累积时间做 0～多次固定物理步；
    做 1 次普通帧更新；
    提交本轮需要绘制的 Viewport；
    按 VSync/帧率限制等待或继续；
}
```

这解释了为什么游戏“没有你的 `while` 仍然会动”：C# 节点脚本只是被主循环叫到。Godot 源码中平台循环调用 `Main::iteration()`；该函数安排物理步、普通处理，并在需要时调用 `RenderingServer::draw()`。[Godot 主循环源码](https://github.com/godotengine/godot/blob/4.6/main/main.cpp)

### 真实时间怎样变成固定物理步

设物理频率为 60 Hz，一个物理步约 `1 / 60 = 0.01667` 秒。主循环记录每轮经过的真实时间，把它累进物理时钟；累积够一步就执行一个固定步，不够就等待后续迭代。这是理解模型，不是 Godot 的逐行源码：

```text
physics_step = 1 / 60 秒
accumulator += 本轮经过的真实时间
while (accumulator >= physics_step 且未超过本轮安全上限) {
    调用节点的 _PhysicsProcess(physics_step)
    让物理服务推进一步
    accumulator -= physics_step
}
调用节点的 _Process(本轮帧间隔)
安排渲染
```

例如目标 120 FPS、物理 60 Hz，理想情况下大约每两个显示帧有一个物理步。如果某轮耗时 40 ms，可能需要补两个物理步；Godot 也设有每帧最大物理步等保护，避免无限追赶。**“一帧”有显示帧和物理帧两种语境，讨论性能与运动时一定说清楚。**

| 显示帧 | 真实时间推进（示意） | 物理步数 | 普通 `_Process` | 渲染 |
| --- | ---: | ---: | ---: | ---: |
| 1 | 8.3 ms | 0 | 1 | 1 |
| 2 | 8.3 ms | 1 | 1 | 1 |
| 3 | 8.3 ms | 0 | 1 | 1 |
| 4 | 8.3 ms | 1 | 1 | 1 |

实际帧间隔、VSync、物理插值和系统负载会让这个表不完全整齐。显示帧多于物理步时，开启物理插值可让画面在两个物理状态之间更平滑；插值只改变显示效果，不把物理模拟变成 120 Hz。[物理插值](https://docs.godotengine.org/en/stable/tutorials/physics/interpolation/using_physics_interpolation.html)

### 把一次按键算到屏幕位置

假设玩家 `GlobalPosition.X = 120`，相机中心 X = 100、缩放 = 1，Viewport 宽 1280；本次物理步开始时，`Input.IsActionPressed("move_right")` 为真，代码给 `CharacterBody2D.Velocity.X = 120` 像素/秒。若这一步 `delta = 1/60` 秒且没有碰撞：

```text
物理位移 = 120 × (1/60) = 2 世界单位
玩家新世界 X = 122
简化屏幕 X = 640 + (122 − 100) = 662
```

下一次渲染用新的世界坐标生成画面，精灵中心大致在屏幕 X=662。这不是 C# 在第 662 个屏幕像素写颜色；C# 给出位置，Camera/Viewport 做坐标映射，渲染管线完成像素计算。如果相机同时跟随玩家到 X=122，玩家又会保持在屏幕中心附近，背景看起来向左移动。这个例子把[04｜输入/物理](04-输入物理与导航.md)、[05｜相机](05-坐标相机与视口.md)和[06｜渲染](06-渲染材质与Shader.md)连起来。

### 输入处于哪一步

窗口系统产生鼠标、键盘等事件，Godot 可缓冲/合并事件，再交给相应 Viewport 分发。`_Input()` 和 `_UnhandledInput()` 是**事件回调**；`Input.IsActionPressed()` 是**读取当前输入状态**。按键事件不等于固定每帧一次，一个显示帧里可能有多个事件，也可能没有。UI 可以消费事件，因此世界输入通常放在 `_UnhandledInput()`。输入的更细路径见[04｜输入与物理](04-输入物理与导航.md)。

### CPU、GPU 与显示器不是一个同步函数

`_Process()` 改节点状态，渲染服务据此准备绘制；GPU 可能异步处理命令，窗口系统随后呈现完成的缓冲图像。打开 VSync 时，呈现受显示刷新节奏约束；关闭 VSync 也不等于所有硬件都会按同一频率运行。Profiler 中“逻辑耗时”和“渲染耗时”需要分开看。深入流程见[06｜渲染](06-渲染材质与Shader.md)。

## 2. 生命周期回调

| Godot C# | Unity 近似概念 | 使用时机 |
| --- | --- | --- |
| `_EnterTree()` | `OnEnable`/Awake 的一部分 | 节点刚进入树，不能假定所有子节点都 Ready |
| `_Ready()` | `Start` 的一部分 | 本节点及子节点完成进入和准备；获取子节点引用 |
| `_Input(InputEvent)` | 输入事件入口 | 抢先处理原始事件 |
| `_UnhandledInput(InputEvent)` | 未被 UI 消费的输入 | 游戏世界的点击、快捷键 |
| `_PhysicsProcess(double delta)` | `FixedUpdate` | 物理运动、需要固定频率的逻辑 |
| `_Process(double delta)` | `Update` | 视觉跟随、非物理计时、界面表现 |
| `_ExitTree()` | `OnDisable`/OnDestroy 的一部分 | 退出场景树，解除外部长寿命订阅 |

进入树时 `_EnterTree()` 通常先父后子；`_Ready()` 通常先子后父。因此父节点在自己的 `_Ready()` 中可以访问已准备好的子节点。再次把同一节点移出再加入树，不要想当然认为 `_Ready()` 会重新运行；需要时可调用 `RequestReady()`，并重新检查状态管理。[SceneTree 文档](https://docs.godotengine.org/en/stable/tutorials/scripting/scene_tree.html)

```csharp
using Godot;

public partial class Mover : Node2D
{
    [Export] public float Speed { get; set; } = 120f;

    public override void _Ready()
    {
        GD.Print($"Ready: {Name}");
    }

    public override void _Process(double delta)
    {
        // 普通非物理运动示意；涉及碰撞时改用物理节点和 _PhysicsProcess。
        Position += Vector2.Right * Speed * (float)delta;
    }
}
```

`delta` 是该回调上次执行以来的秒数。速度单位如果是“像素/秒”，位移应为 `速度 × delta`。物理移动不要先乘 `delta` 再赋给 `CharacterBody2D.Velocity`：它的 `Velocity` 本身是速度，`MoveAndSlide()` 会按物理步处理位移。

## 3. 固定更新与普通更新如何分工

- **物理更新**：碰撞、角色运动、射线查询、施加力、物理有关的目标检测。
- **普通帧更新**：纯视觉插值、UI 文本、与显示帧同步的特效；如果不需要每帧检查，优先用事件/信号。
- **计时器**：延迟触发、冷却、生成间隔。`Timer` 节点适合可视化配置；`SceneTree.CreateTimer()` 适合一次性等待。
- **动画**：属性随时间变化优先考虑 `AnimationPlayer` 或 Tween，少写重复的手动插值循环。

```csharp
public override async void _Ready()
{
    // 演示一次性延迟。生产代码需考虑节点在等待期间被释放的情况。
    await ToSignal(GetTree().CreateTimer(0.5), SceneTreeTimer.SignalName.Timeout);
    if (IsInsideTree()) GD.Print("半秒后触发");
}
```

## 4. 暂停、时间缩放和处理模式

`GetTree().Paused = true` 暂停场景树中通常的处理和物理行为，但节点的 `ProcessMode` 可决定暂停时是否继续运行。暂停菜单通常需要继续处理输入；不要把菜单放在会一起停止的模式里。`Engine.TimeScale` 可以影响游戏时间，用于慢动作；它不是所有计时或网络逻辑的可靠“真实时钟”。需要真实时间时，明确选择不受时间缩放影响的计时方式。

`ProcessMode`、物理插值、最大追赶步数等高级配置会影响细节，先掌握“固定物理步 + 可变显示帧”的模型。物理模拟默认不保证跨机器完全确定性，别把它当作锁步联网的天然基础。[物理简介](https://docs.godotengine.org/en/stable/tutorials/physics/physics_introduction.html)

## 5. 与 Unity 不同的习惯

- 不需要有一个巨大的 `GameManager.Update()` 扫描所有对象；对象可以在自己的节点回调中工作，系统间用信号通信。
- 不要让每个对象每帧搜索树；在 `_Ready()` 缓存节点引用，在变化时通过信号更新。
- 不要依赖不同节点 `_Process()` 的偶然顺序来保证业务规则；必要时用 `ProcessPriority`、显式调度或信号。
- 在物理回调中修改碰撞结构有时会触发“物理空间正在刷新”限制；可用 `CallDeferred()` 或延后到安全时点。
