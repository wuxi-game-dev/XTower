# 00｜从双击游戏到第一帧：把整台机器串起来

本章是整套手册的主线。假设你在 Windows 上双击**已导出的 Godot 4 桌面游戏**。其他桌面系统的概念相同，具体系统调用和初始化细节会不同。编辑器里按 F5 也会启动游戏进程，但还会经过编辑器、调试连接和资源导入等额外步骤。下文用 Godot 4.6 的官方源码作为可核对的实现例子；小版本可能调整内部顺序，概念模型不等于稳定的底层调用契约。

若你双击的是 **Godot 编辑器**，同样先有操作系统进程、窗口和引擎初始化；随后运行的是项目管理器或编辑器自己的场景与工具界面。打开项目时编辑器还会扫描并导入资源、解析脚本等。按 F5 后通常另起游戏运行进程，通过调试连接把错误和远程场景树显示回编辑器。以下时间线聚焦那个真正运行游戏的进程，避免把“编辑器显示了一个窗口”和“游戏已经完成第一帧”混为一谈。

先纠正一句常见说法：**操作系统先创建进程；窗口不是操作系统主动送给游戏的。Godot 初始化到显示系统时，通过平台接口向操作系统请求创建窗口。** 窗口出现，也不代表第一帧游戏画面已经绘制完。

## 一张时间线

```text
双击可执行文件
  │
  ├─ ① 操作系统创建进程，加载可执行文件与依赖，进入 Godot 入口
  ├─ ② Godot 读取启动参数与项目设置，初始化核心系统
  ├─ ③ 选择显示后端与渲染器，请求操作系统创建主窗口
  ├─ ④ 创建渲染设备/窗口显示目标，初始化物理、音频、输入等服务
  ├─ ⑤ 创建 SceneTree 与根 Window/Viewport
  ├─ ⑥ 加载 Autoload，再加载并实例化主场景
  ├─ ⑦ 节点进入树：_EnterTree → 子节点准备 → _Ready
  ├─ ⑧ 运行循环：事件、固定物理步、普通帧逻辑
  ├─ ⑨ 渲染服务器向 GPU 提交绘制工作
  └─ ⑩ GPU 生成图像，系统把它呈现在窗口；此后重复 ⑧～⑩
```

这是一条**教学用因果链**。真实引擎会穿插线程、消息队列、同步、延迟加载和平台特例；不要把每个项目都想成十个完全串行的函数调用。Godot 的入口与主循环可直接在 [Godot `main/main.cpp`](https://github.com/godotengine/godot/blob/4.6/main/main.cpp) 和 [SceneTree 文档](https://docs.godotengine.org/en/stable/tutorials/scripting/scene_tree.html)中核对。

## ① 双击后，操作系统做什么

文件管理器收到双击，要求操作系统启动可执行文件。操作系统创建**进程**：分配虚拟地址空间，装载程序代码和需要的库，建立主线程与基本运行环境，再转入程序入口。此时内存里有了一个正在执行的 Godot 程序，但不必已有游戏窗口。

在 Unity 里，导出后的 Player 也经历类似过程。你写的 `MonoBehaviour.Start()` 或 Godot 的 `_Ready()` 都远晚于这一步。

Godot 可执行文件接下来需要找到项目数据。编辑器开发时它从项目目录读 `project.godot` 和 `res://`；导出后资源通常来自打包的 PCK/嵌入数据。`project.godot` 中的窗口大小、主场景、渲染方法等设置会影响后续初始化。并非所有贴图、声音和场景都必须在启动瞬间加载；很多资源会按需加载。

## ② 引擎“搭基础设施”

Godot 初始化自己的对象类型系统、项目设置、资源加载、脚本语言支持、输入、物理、渲染、音频、导航等模块。这里的“Server”是引擎内部服务接口：例如节点 `Sprite2D` 最终需要渲染服务绘图，`CharacterBody2D` 最终需要物理服务处理运动。普通开发通常通过节点访问这些服务。

C# 项目还要启动相应的 .NET 运行环境并装载游戏程序集。**C# 类存在于程序集中，不等于它的节点实例已经在场景树里。** 只有加载并实例化场景，附着脚本的节点才开始收到生命周期回调。

## ③ 窗口究竟是谁创建的

Godot 根据项目配置和平台能力选择显示后端，并经 `DisplayServer` 请求创建窗口。Windows 平台最终会调用系统窗口 API；Linux/macOS 使用各自的平台接口。窗口有标题、尺寸、位置、焦点、输入消息等系统属性。

同时，引擎选择渲染器和图形驱动，例如 Forward+ 配合可用的 Vulkan/Direct3D 12/Metal 后端，或 Compatibility 使用 OpenGL。图形 API 与驱动帮助 Godot 创建 GPU 设备、绘制目标和用于显示图像的缓冲。Godot 源码中的 `DisplayServer::create(...)` 是这一阶段的可见入口；[DisplayServer 类参考](https://docs.godotengine.org/en/stable/classes/class_displayserver.html)解释了它的窗口职责。

**窗口 ≠ 画面。** 刚创建的窗口可能暂时只有背景色或启动画面。要出现角色，后面还得有场景、可见节点、相机/画布、渲染命令和 GPU 输出。

## ④ 根 Window、Viewport、SceneTree 如何接起来

Godot 默认用 `SceneTree` 作为游戏的 `MainLoop`。它管理当前活着的节点、输入分发、暂停、组、场景切换与更新回调。SceneTree 有一个根 `Window`；`Window` 同时是 `Viewport`，也就是**一块可以接收输入并生成图像的渲染区域**。

```text
操作系统窗口（屏幕上的本机窗口）
  ↕ DisplayServer（尺寸、焦点、输入、呈现）
根 Window / Viewport（Godot 的渲染与输入区域）
  └─ SceneTree 中的节点
       └─ 主场景及其子场景
```

`GetTree().Root` 指向根 Window/Viewport；`GetTree().CurrentScene` 指向当前主场景的根节点。二者不是同一个对象。以后你建 `SubViewport` 时，就会有额外的渲染区域，但不会自动多出一个操作系统窗口。[SceneTree 根 Viewport](https://docs.godotengine.org/en/stable/tutorials/scripting/scene_tree.html)

## ⑤ 主场景何时变成“活的”

Godot 从项目设置读到主场景路径，通过 `ResourceLoader` 加载保存的 `PackedScene`，实例化出一棵节点树，把它加入 SceneTree。配置的 Autoload 会在主场景之前加载并加入根树。**`.tscn` 文件是模板；实例节点才是运行时对象。**

假设主场景是：

```text
Main : Node2D
├─ Player : CharacterBody2D
│  └─ Sprite2D
└─ Camera2D
```

它进入场景树时，`_EnterTree()` 自上而下通知；子节点先完成 `_Ready()`，父节点后完成 `_Ready()`。因此 `Main._Ready()` 可以访问已 Ready 的 `Player`。这时你在 Unity 里的 `Awake/Start` 经验可以辅助理解，但 Godot 的准确顺序以自身生命周期为准。节点进入树之前，不该假设 `GetTree()`、全局变换或信号连接都已可用。

## ⑥ 第一轮“游戏泵”究竟泵了什么

平台层持续处理窗口消息：鼠标、键盘、窗口大小、最小化、关闭等。Godot 把输入转为 `InputEvent`，交给 Viewport 和场景树分发。之后每轮引擎迭代会根据经过的时间安排固定物理步、普通帧处理以及渲染；实际还包含延迟调用、消息队列、导航、音频与调试器工作。

```text
第 N 轮迭代（概念）
├─ 处理或刷新已缓冲输入事件
├─ 若累积时间足够：执行 0～多次固定物理步
│  ├─ 脚本 _PhysicsProcess(delta)
│  ├─ 物理服务推进碰撞/运动
│  └─ 传播相关查询、信号和延迟调用
├─ 脚本 _Process(delta) 与普通帧任务
├─ 收集 Viewport 内需要绘制的对象并提交渲染
└─ 帧限速/同步；若收到退出请求，结束循环
```

例如显示设备 144 Hz、物理配置 60 Hz：某些显示帧没有新的物理步；显示卡顿时，一轮可能补做多个物理步。不能说“每画一帧就执行一次物理”。更精确的时序见[02｜主循环](02-主循环与生命周期.md)。Godot 的 `Main::iteration()` 也显示了固定步循环、普通 `process` 和 `RenderingServer::draw` 等阶段。[源码](https://github.com/godotengine/godot/blob/4.6/main/main.cpp)

## ⑦ 一张图怎样真的出现在窗口里

设主场景里有 `Sprite2D`：

1. 贴图资源被加载或取自缓存，节点持有贴图引用、位置、颜色、可见性等状态。
2. 相机与画布/Viewport 把世界坐标映射到画面区域。没有物体落在视野内，画面可能只有背景。
3. 渲染服务组织绘制数据。2D 精灵可理解为带纹理的矩形（三角形），材质决定 Shader 与混合参数。
4. CPU 向图形 API 提交命令；GPU 执行顶点变换、光栅化、片元着色等工作，把像素写入渲染目标。
5. 最终图像被提交到窗口的显示缓冲，由图形系统和桌面合成器呈现到屏幕。呈现可能受 VSync 和缓冲队列影响，不必与 C# 回调在同一瞬间完成。

所以，`Sprite2D.Position = ...` 是在**改下一次渲染要读取的状态**，不是立刻在操作系统窗口上画一个点。完整管线见[06｜渲染](06-渲染材质与Shader.md)；相机如何决定屏幕位置见[05｜坐标与相机](05-坐标相机与视口.md)。

## ⑧ 音频在哪里

音频不是“画面的一部分”。`AudioStreamPlayer` 向音频系统提供声音数据，音频服务混合各路 Bus，平台音频接口把样本送到设备。画面 60 FPS 不意味着声卡也每 1/60 秒播放一次声音；音频有独立的缓冲和时序。点击后播放音效，是游戏逻辑请求音频系统处理，不需要等 Shader 绘制。

## ⑨ 关闭游戏时发生什么

点击窗口关闭按钮会变成窗口事件；Godot 可通知节点并退出 SceneTree。节点退出树时有 `_ExitTree()`；引擎随后释放场景、服务和平台资源，进程结束。强制结束进程、崩溃或系统断电不保证这些回调执行，因此关键存档不能只放在退出回调里。

## 用一个空项目亲眼验证

创建**单独的 Godot 4 .NET 空项目**（不用本仓库）：

1. 新建 `Node2D` 根场景并保存为 `Main.tscn`，设置为主场景。
2. 给根节点挂 `BootProbe.cs`；添加一个 `Sprite2D`，给它指定任意贴图。
3. 按 F5 运行，观察输出；再打开 Remote 场景树，对照 `Window → Main → Sprite2D`。
4. 移动精灵、改变窗口尺寸、按一个键，观察日志与画面；关闭窗口观察 `_ExitTree()`。

```csharp
using Godot;

public partial class BootProbe : Node2D
{
    private int _processCount;
    private int _physicsCount;

    public override void _EnterTree() => GD.Print("进入场景树");

    public override void _Ready()
    {
        GD.Print($"Ready；窗口尺寸 = {GetWindow().Size}");
        QueueRedraw();
    }

    public override void _Input(InputEvent @event)
    {
        if (@event is InputEventKey { Pressed: true, Echo: false } key)
            GD.Print($"键盘事件：{key.Keycode}");
    }

    public override void _PhysicsProcess(double delta)
    {
        if (++_physicsCount <= 3)
            GD.Print($"物理步 {_physicsCount}，delta={delta:F4}");
    }

    public override void _Process(double delta)
    {
        if (++_processCount <= 3)
            GD.Print($"显示帧 {_processCount}，delta={delta:F4}");
    }

    public override void _Draw()
    {
        DrawLine(Vector2.Zero, new Vector2(80, 0), Colors.Red, 3);
        GD.Print("重绘当前 CanvasItem");
    }

    public override void _ExitTree() => GD.Print("退出场景树");
}
```

观察重点：`_Ready()` 发生在主循环持续更新之前；`_Draw()` 是 CanvasItem 需要重绘时调用，不保证每个显示帧都调用；物理步计数与显示帧计数不一定同步。这个实验比背回调表更能建立“游戏泵”的直觉。

## 本章最后的因果链

```text
进程存在 → 引擎初始化 → 请求窗口与 GPU 目标 → SceneTree 与场景存在
→ 输入使状态变化 → 物理/普通帧推进状态 → 渲染把状态变成像素
→ 图像呈现在窗口 → 下一轮继续
```

如果其中一环出问题，就按这一环排查：没有窗口是平台/显示初始化；有窗口但没对象可能是场景、可见性或相机；对象显示但不动可能是输入或循环；会动但卡顿则看物理和渲染的帧时间。
