# 10｜其他系统与深入方向

前九章覆盖最常使用的主干。本章给出其余系统的入口，帮助你知道“这个问题该去哪个模块找”，而不是在一个游戏里提前实现所有系统。

## 1. 2D 世界制作：TileMapLayer、地形与排序

重复铺设的地面、墙、装饰常用 `TileMapLayer`，配合 `TileSet` 定义切片、碰撞、导航和自动拼接。TileMap 是世界内容的组织方式，不自动替你决定“玩家能不能通过”“敌人如何寻路”；碰撞与导航仍须配置并验证。多层地图常分为背景、可碰撞地形、前景遮挡。`Y Sort` 可让角色按 Y 位置决定前后关系，但要理解其作用范围与节点层级。

学习顺序：先手放少量图块 → 加碰撞 → 加导航 → 再研究自动地形规则和运行时改图块。[TileMap 文档](https://docs.godotengine.org/en/stable/tutorials/2d/using_tilemaps.html)

## 2. 3D 世界制作：Mesh、环境与可见性

3D 场景的基础节点包括 `MeshInstance3D`、`CollisionShape3D`、`Camera3D`、灯光、`WorldEnvironment`。网格负责外观，碰撞形状负责物理；材质负责表面，环境负责天空、反射、色调映射等整体照明。导入 Blender 等 DCC 资产时，要检查坐标轴、尺寸、骨骼、动画、贴图与材质转换。

性能问题通常围绕可见性、阴影、透明材质、灯光、网格复杂度和纹理尺寸。先使用内置材质和环境，确定视觉目标后再定制 Shader。[3D 教程](https://docs.godotengine.org/en/stable/tutorials/3d/)

## 3. 网络：复制状态不是复制画面

Godot 有高级多人游戏 API、RPC、多人同步节点和底层网络接口。联机的核心问题不是“把场景树发过去”，而是谁拥有权威状态、客户端何时预测、延迟如何处理、断线后怎样恢复。`MultiplayerSpawner` 和 `MultiplayerSynchronizer` 能帮助管理生成和属性同步，但不能自动设计公平性、反作弊和游戏协议。

先做两个本地实例之间的最简单移动同步，再研究服务器权威、插值、预测和状态回滚。不要假设本机双开成功就说明公网连接、NAT、重连与安全问题已解决。[多人游戏文档](https://docs.godotengine.org/en/stable/tutorials/networking/high_level_multiplayer.html)

## 4. 国际化与可访问性

多语言不仅是替换字符串：还涉及动态文本长度、字体字形、复数规则、日期数字格式、语音/字幕、UI 布局。Godot 可导入翻译资源并通过 `TranslationServer` 选择语言。界面设计阶段就应让容器接纳更长文本。键位重绑定、色盲友好标记、字幕和字体缩放也是游戏可访问性的重要部分。[国际化文档](https://docs.godotengine.org/en/stable/tutorials/i18n/)

## 5. 线程与后台任务

大资源处理、路径预计算或网络 I/O 可能需要后台工作，但**活动中的场景树不是任意线程安全的数据结构**。工作线程适合计算或准备独立数据；结果回主线程后再安全地修改节点。把“CPU 重计算”与“Godot 节点操作”分开，是线程设计第一原则。过早引入线程会使节点释放、场景切换和异常处理更难。[线程安全 API](https://docs.godotengine.org/en/stable/tutorials/performance/thread_safe_apis.html)

## 6. EditorPlugin、工具脚本与自定义 Inspector

重复关卡编辑操作可用 `@tool`（C# 的 `[Tool]`）脚本在编辑器中运行；大型工具可写 `EditorPlugin`。这种代码会在编辑器里执行，不能假设游戏运行时状态已存在。修改场景资源或文件前要考虑撤销/重做和版本控制。先证明一项编辑工作重复且耗时，再自动化它。[编辑器插件](https://docs.godotengine.org/en/stable/tutorials/plugins/editor/)

## 7. GDExtension、Server API 与自定义渲染

绝大多数游戏不需要从节点 API 下沉。`RenderingServer`、`PhysicsServer`、`AudioServer` 等是更低层接口，适合特殊批量渲染、物理控制或工具需求；`RenderingDevice` 可以执行更底层 GPU 工作；GDExtension 允许用 C++ 等原生代码扩展引擎。它们增加开发和平台维护成本。遇到明确性能或能力限制时，再决定是否值得使用。[RenderingServer](https://docs.godotengine.org/en/stable/classes/class_renderingserver.html)、[GDExtension](https://docs.godotengine.org/en/stable/engine_details/engine_api/gdextension/what_is_gdextension.html)

## 8. 如何决定下一个模块

| 需求 | 先学 |
| --- | --- |
| 角色在地图中移动且会撞墙 | 输入 + 物理 + Camera |
| 大量可复用敌人/道具 | PackedScene + Resource + Signal |
| 地图由重复图块构成 | TileMapLayer + TileSet |
| 有复杂菜单和多分辨率 | Control + Container + Theme |
| 动画状态增多 | AnimationPlayer + AnimationTree |
| 多人同步 | 状态所有权 + RPC + 同步节点 |
| 卡顿 | Profiler + 可重复场景 + 针对性优化 |
| 编辑工作不断重复 | 工具脚本 + EditorPlugin |

学习 Godot 不以“记住全部类名”为目标。真正的系统理解是：看到需求时能判断它是**状态、场景组织、输入、物理、渲染、音频、UI、资源、平台**中的哪一类，知道从哪里验证与调试。
